# Instant QA → WordPress publishing (Owner approved, activation gated)

Owner requested **2026-10-16**: "Writer viết xong, qua QA là lên WordPress luôn; mười bài thì 2+2+2+2+2". The request is recorded in `config/production-policy.json` as `owner_publish_request`. This is approval of the **desired behavior**, NOT evidence that technical security/SEO prerequisites are satisfied.

## Fast path

1. External AI W1/W2/W3 claims up to TEN unique `PLANNED` topic IDs, writes each 1,600–5,000 useful words on own approved branch/session and submits immutable hash receipts. GitHub does not invent content, call an LLM or simulate a Writer.
2. `Universal writer QA (no WordPress credentials)` runs unit tests, invariants and `scripts/qa_gate.py`: it requires a **fresh complete hash-validated QA receipt for every article**, then marks each article separately PASS or FAIL/REVIEW. Example: ten submitted drafts → eight PASS, two REPAIR. The overall workflow can finish successfully because the *quality evaluation process* completed; the Actions summary explicitly shows how many failed. This does **not** approve or count FAIL/REVIEW content. They remain owned by their Writer and require external AI revision.
3. After a **successful main-push QA run**, `Universal WordPress Publisher` now receives a `workflow_run` event. The publisher refuses failed/pr-event QA and checks that the QA head SHA belongs to the current main history. Direct draft-push launch into Publisher was removed to prevent racing QA. Manual dispatch and 30-minute schedule remain **fallbacks**, not mandatory pauses between pairs.
4. When production prerequisites are actually verified and mode is active, Publisher audits live WordPress, reevaluates factual/source/link/taxonomy/collision QA **live per article**, checks immutable receipt/hash and a fresh main policy, writes durable `POST_INTENT` *before* each WordPress create. It refuses blind retry and reconciles uncertain POST intents.
5. It executes five consecutive 2-article batches, at most **10 new WordPress posts per run**, under the owner-approved `max_new_posts_daily=1000` per UTC day (public and fallback drafts combined); first pair doesn't wait 30 minutes before the next. `max_batches_per_run=5`, `batch_size=2` and `max_new_drafts_daily=1000` apply. The 1,000/day setting is a **ceiling, not a guarantee of 1,000 publications**: the current 10-post/run limit requires 100 successful runs for 1,000 posts, plus 1,000 separately researched, authored, QA-PASS articles; `dry_run` remains OFF for publishing. If category is mismatched, the article becomes a **WordPress draft** under a verified existing fallback category rather than public; no old URLs or posts are overwritten.
6. Every published article must pass readback: public permalink, canonical, browser title, meta description, indexable status, matching content and correct category. A public POST that fails verification remains `NEEDS_RECONCILE` (not silently "SUCCESS").
7. If a batch contains fewer than 10 QA-PASS items, only the available qualified items are posted. For example, 8 PASS + 2 FAIL from a 10-article Writer lease proceeds as **2+2+2+2** once Production is active. FAIL/REVIEW stays in REPAIR and does not block other articles. Missing/stale QA reports or an interrupted evaluation stop the entire job. Writers must revise drafts themselves; GitHub Actions has no AI model to perform textual auto-repair after a chat/agent ends.
