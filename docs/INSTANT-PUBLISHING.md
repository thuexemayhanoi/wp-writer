## Fast path

1. External AI W1–W9 claims up to TEN unique `PLANNED` topic IDs, writes each 1,600–5,000 useful words on own approved branch/session and submits immutable hash receipts. GitHub does not invent content, call an LLM or simulate a Writer.
2. `Universal writer QA (no WordPress credentials)` runs unit tests, invariants and `scripts/qa_gate.py`: it requires a **fresh complete hash-validated QA receipt for every article**, then marks each article separately PASS or FAIL/REVIEW. Example: ten submitted drafts → eight PASS, two REPAIR. The overall workflow can finish successfully because the *quality evaluation process* completed; the Actions summary explicitly shows how many failed. This does **not** approve or count FAIL/REVIEW content. They remain owned by their Writer and require external AI revision.
3. **Backpressure update (2026-10-19):** rapid `posts/drafts/**` commits no longer start a separate QA run per article. A trusted main QA **sweep every five minutes** (or manual dispatch) checks the latest committed drafts; code/config changes still start QA immediately. After successful `main` QA (`schedule`, `workflow_dispatch`, or trusted code `push`), Publisher receives `workflow_run`. It refuses failed/PR-event QA and confirms that the QA SHA is an ancestor of current main. The 30-minute Publisher schedule is a recovery fallback. GitHub schedule executions may be delayed under load; five minutes is the requested cadence, not a guaranteed SLA.
4. When the owner switch is on (`production_enabled=true`, `owner_approval_ref`, `seo_adapter_verified`), Publisher audits live WordPress, reevaluates factual/source/link/taxonomy/collision QA **live per article**, checks immutable receipt/hash and a fresh main policy, writes durable `POST_INTENT` *before* each WordPress create. It refuses blind retry and reconciles uncertain POST intents.
5. It executes five consecutive 2-article batches, at most **10 new WordPress posts per run**, under the owner-approved `max_new_posts_daily=1000` per UTC day (public and fallback drafts combined); first pair doesn't wait 30 minutes before the next. `max_batches_per_run=5`, `batch_size=2` and `max_new_drafts_daily=1000` apply. The 1,000/day setting is a **ceiling, not a guarantee of 1,000 publications**: the current 10-post/run limit requires 100 successful runs for 1,000 posts, plus 1,000 separately researched, authored, QA-PASS articles; publishing is ON. If category is mismatched, the article becomes a **WordPress draft** under a verified existing fallback category rather than public; no old URLs or posts are overwritten.
6. Every published article must pass readback: public permalink, canonical, browser title, meta description, indexable status, matching content and correct category. A public POST that fails verification remains `NEEDS_RECONCILE` (not silently "SUCCESS").
7. If a batch contains fewer than 10 QA-PASS items, only the available qualified items are posted. For example, 8 PASS + 2 FAIL from a 10-article Writer lease proceeds as **2+2+2+2** once Production is active. FAIL/REVIEW stays in REPAIR and does not block other articles. Since 2026-10-17 the same holds for a stray or edited draft (quarantined by the Publisher intake with `INTAKE_REJECTED`, FAIL ticket in QA), an article refused before any write (skipped as BLOCKED) and an earlier uncertain POST (`NEEDS_RECONCILE`, never retried, never blocking others). If WordPress refuses a POST with HTTP 4xx, or the run stops before the POST, the write-ahead intent is withdrawn so the next run retries cleanly; timeouts, 5xx and failed readbacks stay uncertain. Missing/stale QA reports or an interrupted evaluation stop the entire job. Writers must revise drafts themselves; GitHub Actions has no AI model to perform textual auto-repair after a chat/agent ends.
